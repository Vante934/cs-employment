# 设计决策记录 (Architecture Decision Records)

本文档记录项目中的关键技术决策、理由、权衡和后果。

## 格式说明

每个决策包含：
- **决策编号**：ADR-XXX
- **状态**：提议/已接受/已弃用/已替代
- **日期**：决策日期
- **背景**：为什么需要做这个决策
- **决策**：具体选择了什么
- **理由**：为什么这样选择
- **后果**：这个决策带来的影响（正面和负面）
- **替代方案**：考虑过但未选择的方案
- **验证方法**：如何确认这个决策是正确的

## ADR-001: 选择 FAISS 作为向量检索引擎

**状态**: 已接受  
**日期**: 2025-01-XX  
**决策者**: 开发团队

### 背景

知识库需要对文本切片进行语义检索，需要选择一个向量索引方案。主要候选：
- FAISS (Facebook AI Similarity Search)
- ChromaDB
- Qdrant
- Milvus
- Pinecone (云服务)

### 决策

选择 **FAISS** 作为向量检索引擎。

### 理由

**优势**：
1. ✅ **成熟稳定**：Meta 开源，生产环境广泛验证
2. ✅ **本地化**：无需外部服务，符合单用户本地部署需求
3. ✅ **高性能**：百万级向量毫秒级检索，C++ 实现
4. ✅ **轻量**：仅需 faiss-cpu，依赖少
5. ✅ **灵活**：支持多种索引类型（Flat、IVF、HNSW）
6. ✅ **持久化简单**：一个 .faiss 文件即可保存索引
7. ✅ **社区活跃**：文档完善，问题易解决

**限制**：
- ❌ 无内置元数据管理（需自行维护 chunk_mapping）
- ❌ API 相对底层（需封装）

### 后果

**正面**：
- 性能满足首期需求（< 50,000 chunks）
- 依赖简单，安装快速
- 可选升级到 GPU 版本（faiss-gpu）

**负面**：
- 需要自行实现 chunk_id 与 vector_id 的映射
- 删除向量时只能标记为无效，不能真正删除（需定期重建索引）

### 替代方案

#### 方案 A: ChromaDB
- ✅ 更易用，内置元数据管理
- ✅ 一体化存储（向量+元数据）
- ❌ 依赖更多（DuckDB、ClickHouse 客户端等）
- ❌ 作为数据库而非纯索引库，偏重
- **结论**：如果 FAISS 映射管理复杂，可切换

#### 方案 B: Qdrant
- ✅ 专业向量数据库，功能丰富
- ❌ 需要运行独立服务（Docker 或二进制）
- ❌ 对单用户场景过重
- **结论**：不适合本地轻量部署

#### 方案 C: Pinecone
- ✅ 托管服务，无需维护
- ❌ 需要外网访问和 API Key
- ❌ 有成本（免费额度有限）
- ❌ 不符合本地化需求
- **结论**：不符合技术方案

### 验证方法

1. **性能测试**：10,000 chunks，检索耗时 < 100ms（CPU）
2. **持久化测试**：重启后索引可正常加载和检索
3. **准确性测试**：top-5 检索结果与预期相关

## ADR-002: 使用 sentence-transformers 进行文本向量化

**状态**: 已接受  
**日期**: 2025-01-XX

### 背景

需要将文本切片和用户查询转换为向量，主要候选：
- sentence-transformers (开源)
- OpenAI Embeddings API
- Cohere Embeddings API
- 自训练模型

### 决策

使用 **sentence-transformers** 库，模型选择 **all-MiniLM-L6-v2**。

### 理由

**sentence-transformers 优势**：
1. ✅ **开源免费**：无 API 调用成本
2. ✅ **本地运行**：无需外网，隐私友好
3. ✅ **模型丰富**：提供多种预训练模型
4. ✅ **中英文支持**：多语言模型表现良好
5. ✅ **易用**：API 简洁，上手快

**all-MiniLM-L6-v2 模型优势**：
1. ✅ **轻量**：80MB，加载快
2. ✅ **快速**：CPU 可用，单次向量化 < 50ms
3. ✅ **384 维**：存储友好（vs 1536 维）
4. ✅ **效果好**：MTEB 基准测试中表现优秀

### 后果

**正面**：
- 零 API 成本
- 响应快速（无网络延迟）
- 数据不出本地

**负面**：
- 中文效果不如 OpenAI text-embedding-3-small
- 需要占用约 200MB 内存

### 替代方案

#### 方案 A: OpenAI text-embedding-3-small
- ✅ 中英文效果更好
- ✅ 1536 维，语义更丰富
- ❌ 需要 API Key 和外网
- ❌ 成本：$0.02 / 1M tokens（约 750,000 中文字符）
- ❌ 每次检索需联网
- **结论**：不符合本地化和零成本需求

#### 方案 B: 更大的模型（all-mpnet-base-v2）
- ✅ 768 维，效果更好
- ❌ 420MB，加载慢
- ❌ CPU 向量化较慢（~200ms/次）
- **结论**：首期不需要这么高精度

#### 方案 C: 中文专用模型（paraphrase-multilingual-MiniLM-L12-v2）
- ✅ 中文效果更好
- ❌ 体积更大（420MB）
- **结论**：如果中文检索效果不佳，可切换

### 验证方法

1. **准确性测试**：中英文混合查询，top-5 召回率 > 80%
2. **性能测试**：单次向量化 < 100ms（CPU）
3. **内存测试**：模型加载后内存增长 < 300MB

## ADR-003: 扩展现有 SQLite 而非独立数据库

**状态**: 已接受  
**日期**: 2025-01-XX

### 背景

知识库需要持久化元数据（文件记录、切片等），选项：
1. 扩展 Nanobot 现有的 session.db
2. 创建独立的 kb.db
3. 使用 PostgreSQL

### 决策

**扩展现有 session.db**，新增 `kb_*` 前缀的表。

### 理由

1. ✅ **复用已有机制**：Nanobot 已有 SqliteSessionStore，可复用连接池和事务逻辑
2. ✅ **简化部署**：不增加额外数据库依赖
3. ✅ **统一管理**：备份和迁移只需处理一个数据库文件
4. ✅ **避免冲突**：使用 `kb_` 前缀，不与现有表冲突

### 后果

**正面**：
- 开发简单，复用现有 Store 代码
- 用户无需额外配置
- 备份恢复简单

**负面**：
- 知识库和会话数据耦合在一个文件中
- 未来如果需要分离，迁移成本较高

### 替代方案

#### 方案 A: 独立 kb.db
- ✅ 知识库和会话解耦
- ✅ 可独立备份和迁移
- ❌ 需要管理两个数据库连接
- ❌ 事务跨库复杂
- **结论**：首期不需要这种隔离

#### 方案 B: PostgreSQL
- ✅ 功能更强大（全文搜索、并发）
- ❌ 需要运行独立服务
- ❌ 对单用户场景过重
- **结论**：不符合轻量化需求

### 验证方法

1. **兼容性测试**：新表不影响 Nanobot 现有功能
2. **性能测试**：10,000 条记录查询 < 50ms
3. **事务测试**：文件记录和切片的原子性

## ADR-004: 异步任务使用 asyncio.create_task

**状态**: 已接受  
**日期**: 2025-01-XX

### 背景

文件解析和向量化是耗时操作，需要异步执行，不阻塞用户交互。选项：
1. asyncio.create_task()
2. Nanobot Cron 服务
3. Celery
4. 简单的线程池

### 决策

使用 **asyncio.create_task()** 启动异步任务。

### 理由

1. ✅ **简单**：无需额外依赖
2. ✅ **与 Nanobot 一致**：Nanobot 全异步架构
3. ✅ **快速响应**：任务立即启动
4. ✅ **适合首期**：文件量小，并发低

### 后果

**正面**：
- 实现简单，代码少
- 用户体验好（立即反馈）

**负面**：
- ❌ **进程重启丢失任务**：如果在解析中重启，任务丢失
- ❌ **无任务队列**：不支持优先级和限流
- ❌ **无重试**：失败需手动重试

### 替代方案

#### 方案 A: Nanobot Cron 服务
- ✅ 持久化任务定义
- ✅ 重启后可恢复
- ❌ 实现复杂（需集成 Cron binding）
- ❌ 首期过度设计
- **结论**：未来优化可迁移到 Cron

#### 方案 B: Celery
- ✅ 专业任务队列，功能完善
- ❌ 需要 Redis/RabbitMQ
- ❌ 对单用户场景过重
- **结论**：不适合本地轻量部署

### 缓解措施

1. **状态记录**：任务失败时标记 status='failed'，用户可重试
2. **幂等性**：重试不创建重复记录
3. **文档说明**：告知用户重启可能丢失进行中的任务

### 未来优化

当文件量增长（> 100 文件/天）时，考虑迁移到 Cron 服务。

## ADR-005: 文件去重使用 SHA256 哈希

**状态**: 已接受  
**日期**: 2025-01-XX

### 背景

用户可能多次上传相同文件，需要去重避免浪费存储和计算。方案：
1. SHA256 哈希
2. 内容相似度（余弦相似度）
3. 文件名 + 大小
4. 不去重

### 决策

使用 **SHA256 哈希 + UNIQUE 约束**。

### 理由

1. ✅ **精确去重**：内容完全相同才视为重复
2. ✅ **高效**：哈希计算快（< 100ms）
3. ✅ **数据库支持**：UNIQUE 约束自动保证唯一性
4. ✅ **无误判**：不同文件哈希几乎不可能冲突

### 后果

**正面**：
- 完全相同的文件不会重复入库
- 节省存储和计算资源

**负面**：
- 文件内容微小变化（如添加一个空格）会被视为不同文件
- 不支持"相似文件"去重

### 替代方案

#### 方案 A: 内容相似度去重
- ✅ 可识别微小变化的文件
- ❌ 实现复杂（需向量相似度计算）
- ❌ 阈值难定（多相似算重复？）
- **结论**：首期不需要

#### 方案 B: 文件名 + 大小
- ✅ 简单
- ❌ 误判高（不同内容可能同名同大小）
- **结论**：不可靠

### 验证方法

1. **精确重复**：上传相同文件两次，第二次提示已存在
2. **不同内容**：修改文件内容后，视为新文件
3. **不同文件名**：相同内容不同文件名，识别为重复

## ADR-006: 文本切片参数 chunk_size=500, overlap=50

**状态**: 已接受  
**日期**: 2025-01-XX

### 背景

需要将长文本切分为适合向量化和检索的片段。关键参数：
- chunk_size：每个切片的字符数
- overlap：相邻切片的重叠字符数

### 决策

- **chunk_size = 500 字符**
- **overlap = 50 字符**

### 理由

**chunk_size = 500**：
1. ✅ **语义完整**：约 1-2 个段落，足以包含完整语义
2. ✅ **不超限**：模型输入限制通常 512 tokens，500 字符安全
3. ✅ **检索精度**：不会太长（噪音多）也不会太短（上下文少）

**overlap = 50**：
1. ✅ **防止切断**：关键信息跨切片时，重叠部分保证不丢失
2. ✅ **不冗余**：10% 重叠适中，不会显著增加存储

### 后果

**正面**：
- 检索召回率高（关键信息不被切断）
- 向量化效果好（语义完整）

**负面**：
- 存储增加 10%（因为重叠）
- 很长的句子可能被切断

### 替代方案

#### 方案 A: chunk_size=1000, overlap=100
- ✅ 上下文更丰富
- ❌ 可能超过模型限制
- ❌ 检索噪音增加
- **结论**：首期不需要这么长

#### 方案 B: 按句子切分（智能切分）
- ✅ 不会切断句子
- ❌ 实现复杂（需 NLP 分句）
- ❌ 句子长度不均
- **结论**：未来优化可考虑

### 可调整性

参数保存在 `kb_config` 表，可动态调整。调整后需重新解析文件。

## ADR-007: 首期不支持 OCR 和图片知识库

**状态**: 已接受  
**日期**: 2025-01-XX

### 背景

用户可能上传扫描版 PDF 或包含重要图表的文件。是否支持 OCR？

### 决策

**首期明确不支持 OCR**，仅处理文本型 PDF。

### 理由

**排除理由**：
1. ❌ **复杂度高**：需集成 Tesseract 或云 OCR API
2. ❌ **依赖重**：Tesseract 需系统级安装
3. ❌ **准确性挑战**：中文 OCR 准确率依赖训练质量
4. ❌ **处理慢**：OCR 耗时长（数秒/页）
5. ❌ **非核心需求**：首期聚焦文本知识库

### 后果

**正面**：
- 开发周期短
- 系统简单稳定

**负面**：
- 扫描版 PDF 无法处理
- 用户需自行准备文本型文件

### 缓解措施

1. **文档说明**：明确告知不支持扫描件
2. **错误提示**：检测到扫描件时，提示用户
3. **未来规划**：列入二期功能

### 未来扩展

二期可选方案：
- 集成 Tesseract（本地 OCR）
- 调用云 OCR API（百度/阿里云）
- 集成 PDF 图表提取

## ADR-008: 不开发独立 Web 管理后台

**状态**: 已接受  
**日期**: 2025-01-XX

### 背景

是否需要一个独立的 Web 界面来管理知识库？

### 决策

**首期不开发 Web 管理后台**，所有操作通过飞书机器人完成。

### 理由

1. ✅ **聚焦核心**：飞书交互已足够
2. ✅ **开发周期**：Web 后台需额外 1-2 周
3. ✅ **单用户场景**：本地部署，飞书即可满足
4. ✅ **避免复杂性**：无需处理 Web 认证和前端构建

### 后果

**正面**：
- 交付快
- 维护简单

**负面**：
- 批量操作不便（如一次删除多个文件）
- 无可视化统计

### 缓解措施

通过飞书机器人提供足够的管理命令：
- `/kb list`：列出所有文件
- `/kb delete <file_id>`：删除文件
- `/kb stats`：统计信息

### 未来扩展

如有需求，可复用 Nanobot WebUI 添加知识库管理页面。

## ADR-010: FAISS 索引改用 IndexIDMap2，mapping.json 作为唯一提交点

**状态**: 已接受\
**日期**: F05-A1\
**决策者**: 开发团队

### 背景

F04 使用普通 `IndexFlatIP`，`remove()` 只删除映射，向量仍留在 FAISS 中。重启后 `load()` 发现 `ntotal` 与映射数量不一致而报错，`IndexManager` 捕获后调用 `clear()`，下一次 `save()` 会把空索引写回磁盘。删除文件、强制重建、保存失败回滚都会触发。

### 决策

1. 新建索引使用 `faiss.IndexIDMap2(IndexFlatIP)`，`add_with_ids` 写入显式 ID，`remove_ids` 真正删除向量。
2. `save()` 先把索引写到新的 `faiss-<uuid>.index`，再用临时文件 + `os.replace` 原子替换 `mapping.json`。`mapping.json` 记录 `format`、`index_file`，是唯一提交点。提交成功后才删除旧索引文件。
3. 加载旧格式（无 `format` 字段，固定文件名 `faiss.index`）时，按映射中的位置 `reconstruct` 有效向量，以相同 ID 迁移到 IDMap2；无映射的位置视为孤儿向量丢弃。迁移结果标记为待保存，旧文件在下次成功保存后删除。
4. `clear()` 不再重置 `next_faiss_id`；加载时取 `max(next_faiss_id, 已用最大 ID + 1)`。迁移旧格式时也会以旧 FAISS 的 `ntotal` 作为 ID 水位，即使 mapping 为空且 FAISS 中都是孤儿向量也不会复用历史位置。
5. 加载失败时 `VectorIndex.load()` 不修改实例状态和磁盘文件，`IndexManager.vector_index` 抛出 `RuntimeError`，不再静默清空。

### 理由

- IDMap2 让 `ntotal` 始终等于映射数量，现有一致性校验可以保留并真正起作用。
- 两个文件无法原子写入，以单个原子替换的文件作为提交点，可保证任何时刻磁盘上的映射都指向一个完整的索引文件。
- 不修改 SQLite 表结构，旧 `vector_index_id` 在迁移后保持有效。

### 后果

**正面**：删除后重启不再丢失索引；保存失败不会覆盖可用索引；ID 不会被重复分配。

**负面**：
- 索引损坏时检索不可用，需人工处理后运行 `rebuild_all()`。
- `os.replace` 之后、`fsync` 目录之前断电，Windows 上无法保证目录项持久化（剩余风险）。
- 保存后删除旧文件失败只记 warning，会遗留未引用的 `faiss-*.index`，下次保存时再清理。

### 替代方案

- 保留 `IndexFlatIP`，放宽数量校验并在保存时压缩：需要维护位置到 ID 的重排，改动更大。
- 两个文件依次直接覆盖：中途失败会留下互不匹配的文件。

### 验证方法

`tests/kb/test_kb_index_persistence.py`（真实 faiss-cpu、SQLite、临时目录，确定性向量）。
